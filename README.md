# The network that schedules its own failures

**Kempower challenge · LahtiES Energy Tech Hackathon 2026 · "The Self-Operating Charging Network"**

> *If humans were no longer allowed to continuously operate and maintain a charging network, how would you redesign it?*

Our answer: chargers show warning signs hours before they fail. Our "autopilot":

- spots the warning signs early;
- plans charging around the weak equipment;
- books the repair for the day shift;
- moves charging away from price spikes and grid caps.

This repository is a working Python simulation of five charging sites running **Friday 13.11.2026 with no human decisions**, compared with the baseline, where people are in the loop. It also includes a Streamlit dashboard.

> ⚠️ All data used is **synthetic**, generated by the organisers for the hackathon. Nothing here describes Kempower, its products, customers or any real company.

|---|---|---|

## How it works

```
┌────────────────────────────────────────────────────────────┐
│ CLOUD   prices (day-ahead from 14:00) · fleet schedules ·    │
│         grid notices · technician & spare-part booking       │
└──────────────▲──────────────────────────────┬───────────────┘
               │ decision log, telemetry     │ (may be lost!)
┌──────────────┴──────────────────────────────▼───────────────┐
│ SITE BRAIN (edge)   30-h charging plan, re-solved every      │
│ 15 min · bay & swap planning · health scores & failure ETA · │
│ keeps running on its last copy when the cloud is gone        │
└──────────────┬──────────────────────────────────────────────┘
┌──────────────▼──────────────────────────────────────────────┐
│ CHARGER   hard limits only: dispenser/cabinet max, grid cap, │
│           stop on safety faults                              │
└─────────────────────────────────────────────────────────────┘
```

- **Failure prediction ([`src/health.py`](src/health.py)), explainable.** A straight-line fit on fan speed gives a health state and a predicted trip time, for example *"fan 1640 rpm, falling 57 rpm/h, projected cabinet trip ~Fri 01:32"*. Error bursts flag connector or power-module problems. No black-box ML, and it only uses data from before the current time (tested).
- **Charging plan ([`src/planner.py`](src/planner.py)).** A linear programme (PuLP/CBC) minimises energy cost plus the peak-power fee plus a large penalty for every kWh missing at departure. It respects grid, cabinet and vehicle limits and battery taper. Model-predictive control: the plan is re-solved every 15 minutes and only the next slot is executed. A greedy fallback runs if the solver fails.
- **Bays ([`src/bays.py`](src/bays.py)).** Every bus gets a bay on arrival. When there are more buses than plugs, swaps are planned for the whole night using the fleet schedule, and committed so they don't slip.
- **Repairs ([`src/repairs.py`](src/repairs.py)).** The system picks the part, checks stock and books the technician inside shift hours. It skips today's "remote reset, then wait 2 h" routine. A night call-out happens only if a departure would be missed.
- **Decision log ([`src/events.py`](src/events.py)).** Every decision is a row: time, site, layer, what, why, and whether a person is needed. This is the proof of autonomy.

### Where people stay in the loop, and why
1. **Physical repairs**: a person with the right part, at a planned daytime slot.
2. **Moving buses when there are more buses than plugs.** These are now planned yard moves instead of night firefighting. Our 2029 redesign (one low-cost outlet per vehicle, same power cabinets) brings this to 0 in the simulation.
3. **Approving a risk notice** before 22:00 when a departure can't be met. That is the customer's call.

## Business model
The customer is the **fleet operator** that owns the depot, and it buys **guaranteed departures**:

- a monthly fee per vehicle, plus a share of the measured energy and peak-fee savings;
- the supplier pays a service credit for every under-charged departure caused by a system decision;
- late arrivals and wrong data are the customer's responsibility, proven by the decision log.

See the one-page [service agreement](docs/service_agreement.md).

## Run it

```bash
git clone https://github.com/AbdulZeeshan688/kempower-self-operating-network.git
cd kempower-self-operating-network
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

**Data:** the hackathon dataset (`kempower-challenge-data/`) is *not* included in this repository; it belongs to the organisers. Copy its CSV files into `data/`:
```bash
mkdir -p data && cp /path/to/kempower-challenge-data/* data/
```

Then:
```bash
python -m src.simulate     # all scenarios, about 10 minutes → outputs/
streamlit run app.py       # dashboard
pytest -q                  # 28 tests
```
The results of our run are already committed in `outputs/`, so the dashboard works right after the data is in place.

### Scenarios produced
| Folder in `outputs/` | What it is |
|---|---|
| `autopilot` | Main run: predictive maintenance on |
| `worst_case` | No technician before Fri 08:00: the cabinet really fails |
| `worst_case_oncall` | Same, but the system may call the on-call technician |
| `autopilot_s5_as_configured` | New depot S5 with today's wrong settings |
| `redesign_2029_outlets` | One outlet per vehicle at the bus depots |
| `public_baseline_rules` | Today's rules replayed in our public-hub model (calibration: 70 vs 76 drivers giving up in the data) |

### Tests
The tests check that:
- our KPI code reproduces the organisers' `baseline_kpis.csv` exactly;
- the fan problem is flagged on Thursday during working hours;
- the health model never uses future data;
- the grid limits and the 400 kW cap are never exceeded;
- nothing is bought during the price spike;
- the highway hub keeps charging offline;
- the dashboard renders.

```
tests/                    pytest suite
outputs/                  results of our run
```
